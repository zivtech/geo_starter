## Decision D1 — module release path (OPEN; maintainer)

Proving "the default `stable` floor resolves the module" is **structurally
impossible before the module's stable tag exists on d.o** — so one real-artifact
proof necessarily runs after an irreversible tag. Two sound ways to bound that:

- **D1-a — direct to stable (recommended).** Tag module `1.0.0` directly.
  Justified *only because the module ships zero code change vs. `1.0.0-beta1`*,
  which was already proven by a real released-artifact install on d.o
  (`VALIDATION.md`). The irreversible tag rides on already-field-proven code.
  Gated by the Phase 1 zero-diff assertion.
- **D1-b — rc-first (max caution).** Tag `1.0.0-rc1`, publish, run the
  released-artifact proof against the real d.o RC package, then promote to
  `1.0.0`. Buys one real-artifact proof cycle before the stable tag — but an rc
  is still `< stable`, so it cannot prove *stable-floor resolution* either; the
  stable tag is still cut before that specific assertion goes green. Net: an
  extra release cycle for marginal gain given D1-a's freeze argument.

**RESOLVED 2026-06-08 — D1-b (rc-first), maintainer choice.** Resolved module
phase order (governs over the generic Phase 4 numbering below):
1. Phases 1–3 as written (prep both repos; tag-tree install rehearsal gate).
2. Publish module **`1.0.0-rc1`** (tag + d.o release).
3. **RC released-artifact proof:** fresh install pulling `geo_starter_jsonld
   1.0.0-rc1` from d.o under `minimum-stability: rc`; full Phase 3 DoD set +
   `composer audit`. Catches real-published-artifact / packaging / content-order
   defects while the tag is still **supersedable**.
4. Promote: tag module **`1.0.0`** stable (zero code change vs. rc1/beta1) + d.o
   release.
5. **Stable released-artifact proof** (Phase 5): default `stable` floor, real d.o
   stable module — the first faithful stable-floor resolution proof; gate before
   the recipe tag.
6. Recipe docs flip + tag/publish (Phases 6–7).

Note: an rc is `< stable`, so step 3 proves the real artifact *installs* but not
*default-stable-floor resolution* — that remains step 5. RC-first's value is the
supersedable real-artifact dry run before the irreversible stable tag.

## Sequencing — prove on the *release artifact*, before you publish

A stable tag is effectively irreversible, and beta1 is the warning: the
released-artifact proof caught three install-breakers local validation missed —
because "every prior install rsynced a tree whose directory order happened to
dodge them" (`VALIDATION.md`). **The masking method was the working-tree
re-sync.** So every gate below builds from the *packaged tag tree*, never a
working-tree rsync.

> **Definition — "released artifact":** site-template recipes are **not** served
> by the packages.drupal.org composer facade (`VALIDATION.md`; control:
> `drupal/haven` 404s identically). The recipe's real delivery artifact is the
> **git tag tree as the installer/clone consumes it** — built via
> `git clone --branch <tag> … && rm -rf .git` (per `DEMO_RUNBOOK.md`) or
> `git archive <tag> | tar -x` so `.gitattributes export-ignore` is honored. The
> module's released artifact is its d.o composer package.

## Risks / pre-mortem

- **C1 (was critical, now mitigated):** a working-tree rsync rehearsal + a
  path-repo module dependency would pass green while the released artifact
  breaks — the beta1 trap. Mitigation: all gates build from the packaged tag
  tree; the stable-floor resolution assertion lives in Phase 5 (real artifact),
  not Phase 3 (where path sources bypass `minimum-stability`).
- **Module-then-recipe ordering is mandatory.** The recipe `^1.0` cannot resolve
  the module from d.o until module 1.0.0 is published. Never flip+publish the
  recipe before module 1.0.0 (or rc) exists and Phase 5 is green.
- **No supersede for stable.** beta1→beta2 recovery worked only because beta is
  supersedable; stable is not (M1 rollback = forward `1.0.1`).
- **Mercury/Canvas minor drift** (M3): a minor that changes component prop
  schemas can invalidate the committed Canvas trees / shipped
  `canvas.component.*` configs — reconcile per Phase 2; re-export + re-validate
  if a floor moves.
- **Security coverage:** Community project, not Security-Team-covered. Stable 1.0
  is the prerequisite to *apply* for opt-in coverage — post-1.0 follow-up; do
  not imply coverage in 1.0 copy.
